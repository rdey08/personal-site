## Context

The source language is **J**, and it is worth being precise about what that
means, because the obvious assumption is wrong. J is not a subset of C. It was
designed by the course instructor so the project would not be a standard one,
and Fall 2024 was its first outing.

What it borrows from C is braces, semicolons, and the word `int`. Everything
else is closer to Algol. Programs are `program { }` with `function f(int a) { }`
above them. Calls are statements and never expressions, so `x = f(y)` is not
expressible: you write `call f(y); x = returnvalue;`. `else` is mandatory,
because there is no if-without-else production. There is no multiplication,
division, or modulo. The binary operators are `+ - & | ^` and that is the
complete list. There are no boolean operators, no pointers, no structs, no
floats, and no comments.

A narrow language is not a smaller problem, it just moves where the difficulty
sits. With no arithmetic beyond addition, the interesting work is entirely in
calling convention and control flow.

The AST node structure and the symbol table came from the instructor as a
scaffold. The grammar, the scanner, and the entire code generator are mine.
About 1,700 lines in total, of which the scanner is 217, the grammar 663 across
48 productions, and the AST and code generation 467, with the generator proper
accounting for roughly 230 of those.

## Seven milestones

The fourth is the one I would point at. It is the only milestone that added no
syntax whatsoever, 28 productions in and 28 out, and it was by a distance the
largest change in the project: everything before it was a program that read J
and printed what it had understood, and everything after it was a program that
emitted assembly. Nothing about the language changed. What changed was that
there was now an AST, a tree walk, and a `.s` file at the end of it.

The sixth is the other one, and it is the more interesting failure of my
original design.

## Storage, and why the frame was rebuilt

Through milestone five there were no local variables. Every variable, including
every function parameter, compiled to a single static cell addressed by name:
`lw t0, x` and `sw t0, x, t1`, straight to a label in the data section. It
worked, and the compiler at that point handled nested calls correctly, because
each callee saved the caller's return address on entry and restored it on exit.

Recursion, at that stage, was structurally sound and semantically useless. The
control flow would have returned to exactly the right place. Every activation
would also have shared one cell per variable, so the first assignment inside a
recursive call would overwrite its caller's state.

Local variables are what broke the model. Locals need storage per activation,
which needs a frame with room in it, which needs a stable base register to
address that frame from, because the stack pointer moves during expression
evaluation. So milestone six introduced `fp`, and the seven-line prologue and
epilogue became sixteen.

The frame size is 128 bytes and always has been arbitrary. There is no
frame-size computation anywhere; it is a number large enough not to matter.

<CompilerStackFrame />

Milestone seven then added `return`, and an early return from inside an `if`
block needs somewhere to jump to. So every function's epilogue was hoisted out
into a single shared `func_exit` label. That solved returns cleanly and it also
locked the design: one shared epilogue can only restore the stack by a constant,
so from that commit onward, computing a real frame size was no longer possible
without undoing it. The simplification that made returns easy is the same one
that made the obvious next improvement unreachable.

```asm
fib:
        addi    sp, sp, -128    # fixed frame, every function
        sw      fp, 4(sp)       # save caller's frame pointer
        sw      ra, 0(sp)       # save return address
        mv      fp, sp
        sw      a0, 8(sp)       # spill a0 through a5, always
        ...
func_exit:                      # one epilogue, shared by every function
        mv      sp, fp          # resync: expression temporaries drift sp
        lw      fp, 4(sp)
        lw      ra, 0(sp)
        addi    sp, sp, 128
        ret
```

## Generating code

The target is RV32 running under RARS, the simulator the course used, so the
system calls are RARS numbers rather than Linux ones.

There is no register allocation. `t0` is a universal accumulator and `t1` its
scratch partner, and every binary operation pushes its left operand to the
stack, evaluates the right, pops, and combines. There is no intermediate
representation and no optimiser; the generator walks the AST and prints. You can
see the absence of an optimiser in the output, where an unconditional jump is
followed by a branch that can never be reached, because nothing goes back to
remove it.

Nor is there a semantic pass. Name resolution happens inside the Bison actions
during parsing and amounts to one working check, that a variable is not used
before it is declared. There is a second check for duplicate declarations whose
error path, it turns out, can never be reached. Type checking does not exist at
all, which is survivable in a language with one real type: `string` is in the
grammar but registered as an integer, so string variables are a fiction and only
literals work.

One piece I still like. The relational code generator branches to the then-label
when the condition is true, which means the else block has to be emitted first
and the then block second. Laying the branches out backwards is what lets the
comparison be emitted exactly as written, with no inversion step.

```c
function fib(int n)
{
   int a;
   int b;
   if (n <= 1) then {
      return n;
   } else {
      call fib(n + -1);
      a = returnvalue;
      call fib(n + -2);
      b = returnvalue;
      return a + b;
   }
}
```

Correct at `fib(10)`, and on a linear recursion eight thousand frames deep. The
`n + -1` is not a stylistic choice: `n - 1` does not compile, and that is the
next section.

## Subtraction, twice

Both times this compiler broke, it broke on subtraction, and neither break was
visible until a case appeared that could tell the difference.

The first was in milestone four, where binary operations emitted their operands
in the wrong order. The convention is push-left, evaluate-right, so by the time
both are in registers the left operand is in `t1` and the right in `t0`; the
generated instruction had them the other way around. Addition is commutative, so
with `+` as the only operator the bug was invisible. It was corrected in
milestone five, which is precisely the milestone that introduced subtraction.

The second is the one still in the code. Milestone seven added unary operators,
which means a scanner rule matching `-` and `~`. The rule matching `+ - & | ^`
was already there. Both match `-`, both at length one, and Flex breaks ties by
rule order, so `-` became unary everywhere and binary subtraction quietly
stopped existing. Two test programs that had compiled for weeks no longer did.

The instructive part is what happens when you reach for the obvious fix.
Reordering the two rules restores subtraction and breaks unary negation instead.
The rules are mutually exclusive by construction and no ordering of them can
work, because whether `-` is unary or binary is not a lexical property at all.
It depends on whether the previous token was an operand, and a scanner that
looks at one token cannot know that.

The fix is to stop asking the scanner: emit one token for `-` and let the parser
disambiguate from context, with two productions and a precedence override so
unary binds tighter than binary. What makes it satisfying is where it leads. My
grammar had been conflict-free for six milestones, and milestone seven
introduced exactly one shift/reduce conflict, which I had been treating as
noise. It was this same ambiguity surfacing a phase later. The parser had been
telling me about the scanner's bug the whole time.

The precedence declarations tell the same story from a third angle. There is
only ever one in the grammar, and at milestone four I changed it from left- to
right-associative for no reason I can reconstruct; the grammar has no conflicts
either way. It is harmless for `+ & | ^` and wrong for `-`. So: one precedence
declaration present but unnecessary and subtly wrong, and the one actually
needed, a separate level for unary minus, never written.

Worth being honest about a related thing I did not solve. J never presented the
dangling-else problem, and not because `else` is mandatory. It is because every
block is brace-delimited, so the closing brace pins the attachment structurally
and there is nothing for an `else` to be ambiguous about. That is a property of
the language I was handed, not a problem I noticed or fixed.

## What this shows

The compiler works and its output genuinely runs; I have watched it produce
correct results under the simulator. What it never had was any way of knowing
that automatically. No expected outputs, no assertions, nothing to run a
regression with.

I did eventually write a test suite, six programs covering loops, functions,
return values, bitwise and unary operators, and do-while. I committed it the day
after the final submission. Two of those six do not compile, because of the
subtraction bug from the milestone before. The suite I wrote would have caught
the regression that shipped, had it existed one day earlier. That is the whole
lesson of the project in one commit timestamp, and it is a more useful thing to
have learned than another language feature would have been.

Some of what remains is deliberate simplification: fixed frames, no register
allocation, no optimiser. The rest is not. Declared array sizes are ignored and
every array gets the same allocation, so a large one silently corrupts whatever
follows it. A seventh parameter reads garbage, because only six argument
registers are ever spilled. Assigning to an array element leaks eight bytes of
stack each time, which a function's epilogue quietly absorbs but the program
block does not, so a long enough loop walks the stack pointer into an alignment
fault. There are a few others.
